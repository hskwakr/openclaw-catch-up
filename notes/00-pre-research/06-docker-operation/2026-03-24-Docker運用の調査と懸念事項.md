# OpenClaw Docker運用の調査と懸念事項

*2026-03-24 作成*

## このノートの位置づけ

前回までに構成候補をA'（ZeroClaw+Ollama）/ C'（NanoClaw+Claude+Ollama）/ D（Claude Pro/Max）に絞った。ここでは「OpenClawをDockerで運用する」という方向を前提に、公式対応状況・セキュリティ・パフォーマンス・懸念事項を整理する。

---

## 1. OpenClaw公式Docker対応状況

### イメージとレジストリ

- **公式イメージ**: `ghcr.io/openclaw/openclaw`（GitHub Container Registry）
- タグ: `latest`, `main`, バージョン固有（例: `2026.3.7`）
- ベース: Node.js 24 on Debian Bookworm
- 非rootユーザーで実行（UID 1000という情報は未確認。Dockerfile要確認）
- 公式 `docker-compose.yml` がリポジトリに同梱
- セットアップスクリプト: `./scripts/docker/setup.sh`

### コミュニティ製イメージ

- `coollabsio/openclaw` — 自動ビルド、フル機能
- `deepmehtait/openclaw-docker-secure` — Ollama + Open WebUI + VPN統合
- `blas1n/openclaw-docker` — Tailscale VPN分離
- `alessandrolomanto/openclaw-operator` — Kubernetes向けオペレーター

### 最低リソース要件

- ビルド: RAM 2GB以上（pnpm installがOOM killされる）
- ランタイム: 2GB+（スキル数・会話履歴で増加）
- 推奨: 4GB以上、複雑なワークフローでは8GB

## 2. Docker + Ollama 構成

### ネットワーク接続

OpenClawコンテナからホストのOllamaに接続する場合、`localhost` はコンテナ自身を指すため注意が必要。

| 環境 | 接続先URL |
|------|----------|
| Docker Desktop (Mac/Win) | `http://host.docker.internal:11434/v1` |
| Linux (--network=host) | `http://localhost:11434/v1` |
| docker-compose (同一ネットワーク) | `http://ollama:11434/v1`（サービス名で解決） |

### 構成パターン

**パターン1: ホストOllama + コンテナOpenClaw**
- Ollamaはホストにネイティブインストール（Apple SiliconのGPUを直接利用）
- OpenClawだけDockerで分離
- `host.docker.internal` 経由で接続

**パターン2: docker-compose で両方コンテナ化**
- OllamaもOpenClawもコンテナ内
- 同一Dockerネットワークでサービス名で通信
- ⚠️ OllamaコンテナからMac GPUを使えない（後述）

**パターン3: OpenClaw + Ollama + VPN（セキュア構成）**
- Gluetun等のVPNコンテナをサイドカーとして配置
- 外部通信を全てVPN経由に強制
- ゼロポート公開

## 3. Dockerによるセキュリティメリット

### コンテナ分離がもたらすもの

ホストに直接インストールした場合と比較して:

| 項目 | ネイティブ | Docker |
|------|-----------|--------|
| ファイルシステムアクセス | ユーザーの全ファイル | マウントしたディレクトリのみ |
| SSH鍵・クラウド認証情報 | アクセス可能 | 明示的にマウントしない限り不可 |
| ネットワーク | 制限なし | ネットワークポリシーで制御可能 |
| プロセス空間 | 他プロセスが見える | 分離 |
| ホストの変更 | 可能 | 制限可能 |

### ハードニング手法

```bash
docker run \
  --read-only \                          # ファイルシステムを読み取り専用に
  --cap-drop=ALL \                       # 全Linuxケーパビリティを除去
  --security-opt=no-new-privileges \     # 権限昇格を防止
  --memory=4g \                          # メモリ上限
  --cpus=2.0 \                           # CPU上限
  --tmpfs /tmp \                         # 書き込み可能な一時領域
  -v ~/.openclaw:/home/node/.openclaw \  # 設定のみマウント
  -v ~/workspace:/workspace \            # 作業領域のみマウント
  ghcr.io/openclaw/openclaw
```

### Dockerだけでは不十分な点

**重要: Dockerコンテナはカーネルを共有している。** AIエージェントがコードを生成・実行できる以上、カーネル脆弱性を突く攻撃コードを生成される理論的リスクがある。

直近の実例:
- **CVE-2025-31133, CVE-2025-52565, CVE-2025-52881** — runcの脆弱性（2025年11月公開）。コンテナ初期化中のsymlink race conditionを悪用し、ホストの任意パスをコンテナ内にマウント可能。runc v1.4.0-rc.3, v1.3.3, v1.2.8で修正済み（ランサムウェアグループによる悪用の具体的な報告は確認できず）
- **CVE-2025-9074（CVSS 9.3）** — Docker Desktop固有。悪意あるコンテナがDocker Engineにアクセスし、ホストファイルにアクセス可能。**macOS/Windows のDocker Desktopが影響を受ける**

## 4. M4 Mac Mini 16GBでのDocker運用

### macOSでのDocker = VM上のLinux

Docker Desktop for Macは内部でApple Virtualization Frameworkを使い、軽量LinuxVMを起動する。つまり:

- コンテナ → LinuxVM → macOS の二重分離（セキュリティ上はプラス）
- VMのオーバーヘッド（メモリ・CPU）が発生（パフォーマンス上はマイナス）
- ファイルシステムのバインドマウントはVirtioFS経由でバインドマウント操作で約3倍遅い（書き込み負荷が高い操作ではさらに劣化）（以前は5-6倍だった）

### メモリ配分の現実

16GB統一メモリのうち:

| 用途 | 必要メモリ |
|------|-----------|
| macOS + アプリ | 3-4GB |
| Docker Desktop VM | 2-4GB（設定次第） |
| OpenClawコンテナ | 2-4GB |
| Ollama（ホスト側） | 5-6GB（7Bモデル） |
| **合計** | **12-18GB** |

**結論: 16GBではかなりタイト。** Docker VM + OpenClawコンテナ + Ollama 7Bモデルを同時に動かすと、メモリスワップが頻発する可能性が高い。

### ARM64イメージの問題

- OpenClaw公式イメージがネイティブARM64ビルドを提供しているか未確認
- x86_64イメージをRosetta 2エミュレーションで動かすとパフォーマンスが大幅に低下
- ⚠️ 要確認ポイント

### 代替: OrbStack

Docker Desktopより軽量なOrbStackという選択肢がある:
- Apple Silicon最適化でDocker Desktopよりリソース効率が良いとされる
- 起動が速い
- ただし有料ライセンス（個人利用は無料）

### GPU利用の制約

- Docker on macOSではApple SiliconのGPUをコンテナ内から直接利用できない
- Ollamaをコンテナ内で動かすとCPU推論になり極端に遅くなる
- **→ Ollamaはホストにネイティブインストールし、OpenClawだけDockerに入れるのが現実的**

## 5. Docker vs 他のサンドボックス技術

AIエージェント向けの分離技術を比較:

| 技術 | 分離レベル | パフォーマンス | 起動時間 | メモリオーバーヘッド | 適用場面 |
|------|-----------|-------------|---------|-------------------|---------|
| **Docker** | カーネル共有 | 高速 | <1秒 | 小 | 信頼できるコードの実行 |
| **gVisor** | ユーザー空間syscall | 良好 | <2秒 | syscall 2.2倍遅、ファイルI/Oは最大216倍遅（操作種別依存） | 中程度の信頼度 |
| **Firecracker** | MicroVM（HW仮想化） | 中程度 | ~125ms | 5MiB/VM | **本番AIエージェント推奨** |
| **Kata Containers** | MicroVM（HW仮想化） | 中程度 | やや遅い | カーネルごと | エンタープライズK8s |
| **NanoClaw方式** | Docker Sandboxes（MicroVM） | 中程度 | 依存 | 依存 | セキュリティ重視 |

### 業界の方向性

- Docker社がNanoClawと提携し「Docker Sandboxes」を開発 — AIエージェントをMicroVM内で実行
- Fortune 500の80%がAIエージェントを利用しているという調査あり（Microsoft Security Blog）。Firecracker自体はAWS Lambda等で広く使われているが、「Fortune 500の50%がFirecrackerを採用」という具体的数字は確認できず
- **コンセンサス: 標準Dockerコンテナだけでは、コード生成・実行するAIエージェントには不十分**

## 6. 懸念事項まとめ

### 確実に影響するもの

1. **メモリ圧迫**: 16GBでDocker VM + OpenClaw + Ollama 7Bは厳しい。スワップ発生でレスポンス劣化
2. **GPU利用不可**: Docker内のOllamaはCPU推論になる → Ollamaはホスト側に置くしかない
3. **ファイルI/O遅延**: VirtioFS経由のマウントはバインドマウント操作で約3倍遅い（書き込み負荷が高い操作ではさらに劣化）。大量ファイル操作するタスクに影響
4. **セットアップの摩擦**: v2026.3.2以前でセットアップウィザードのハングが報告されている。3.7+推奨

### セキュリティ上の懸念

5. **カーネル共有**: Dockerはカーネルを共有するため、runc脆弱性などで脱出可能（実例あり）
6. **Docker Desktop CVE-2025-9074**: macOS/Windows固有の脆弱性。コンテナからホストファイルにアクセス可能
7. **ボリュームマウント設計**: `~/.openclaw` と作業ディレクトリだけをマウントし、ホームディレクトリ全体をマウントしない注意が必要
8. **Docker Socketの露出厳禁**: `/var/run/docker.sock` をマウントするとホスト完全制御を許す

### 運用上の懸念

9. **ARM64イメージの状態が不明**: x86_64エミュレーションだとパフォーマンス大幅低下
10. **WhatsApp/Telegram接続切断**: 長時間運用でセッションが切れる報告あり
11. **ブラウザ自動化**: Docker内でのブラウザ操作は追加のサイドカー（CDP + VNC）が必要

## 7. 構成案の再評価

### Option E: OpenClaw（Docker）+ Ollama（ホスト）— M4 Mac Mini 16GB

```
┌──────────────────────────────────────┐
│  macOS (M4 Mac Mini 16GB)            │
│                                      │
│  ┌─────────────┐  ┌──────────────┐  │
│  │ Ollama      │  │ Docker VM    │  │
│  │ (ネイティブ) │  │ ┌──────────┐│  │
│  │ Qwen 7B    │◄─┤ │ OpenClaw ││  │
│  │ ~5-6GB     │  │ │ ~2-4GB   ││  │
│  └─────────────┘  │ └──────────┘│  │
│                    │ VM: ~2GB    │  │
│                    └──────────────┘  │
│  OS + アプリ: ~3-4GB                 │
│  合計: 12-16GB（ギリギリ）            │
└──────────────────────────────────────┘
```

**メリット:**
- OpenClawのエコシステム（スキル、チャネル統合）を利用可能
- コンテナ分離でホストファイルを保護
- Ollamaはネイティブ実行でGPU利用可能

**デメリット:**
- メモリがギリギリ。7Bモデルのコンテキスト長を短めに制限する必要あり
- Docker VMのオーバーヘッド
- ファイルI/O遅延

### Option A'（改訂）: ZeroClaw（ネイティブ）+ Ollama（ネイティブ）

前回の推奨構成。Dockerを使わない場合:
- ZeroClaw自体が4MBしかメモリを使わない → Ollamaに最大限リソースを回せる
- deny-by-defaultのアクセス制御で一定のセキュリティ確保
- ただしコンテナ分離はない

### Option E': OpenClaw（Docker）+ クラウドLLM（Claude API）

Ollamaを使わず、LLMはClaude APIに任せる構成:
- ローカルのメモリ圧迫を回避（Ollama不要）
- Docker VM + OpenClaw で 6-8GB程度
- コスト: Claude API従量課金
- セキュリティ: コンテナ分離 + ホストファイル保護

## 8. 判断のための論点

| 問い | Docker寄りの答え | Docker不要寄りの答え |
|------|----------------|-------------------|
| ホストファイルの保護は重要？ | Yes → Docker必須 | ツール制御（tools.deny）で十分なら不要 |
| 16GBのメモリは足りる？ | ギリギリ（Ollama併用だと苦しい） | ネイティブなら余裕あり |
| カーネル共有のリスクは許容？ | 個人利用なら許容範囲内 | MicroVMが必要ならNanoClaw検討 |
| エコシステムは使いたい？ | OpenClawのスキル・チャネルが魅力 | 不要ならZeroClawで十分 |
| Apple Siliconでの最適化は？ | Docker VMのオーバーヘッドがネック | ネイティブが最速 |
