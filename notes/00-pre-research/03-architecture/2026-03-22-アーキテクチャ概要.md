# OpenClaw アーキテクチャ概要

*2026-03-22 作成*

## 全体像: 5つのコンポーネント

OpenClawは「LLMそのもの」ではなく、LLMを中心に据えた**エージェント基盤**。以下の5つのコンポーネントで構成される。

```
┌─────────────────────────────────────────────────────┐
│  チャネル（WhatsApp, Telegram, Slack, Discord, Web） │
└──────────────────────┬──────────────────────────────┘
                       │ メッセージ
                       ▼
┌──────────────────────────────────────────────────────┐
│                   Gateway                            │
│  ┌────────────┐ ┌──────────┐ ┌───────────────────┐  │
│  │Session      │ │Command   │ │Event              │  │
│  │Registry     │ │Queue     │ │Broadcaster        │  │
│  └────────────┘ └──────────┘ └───────────────────┘  │
│  ┌────────────┐ ┌──────────┐                         │
│  │Heartbeat   │ │Cron      │                         │
│  │Runner      │ │Scheduler │                         │
│  └────────────┘ └──────────┘                         │
└──────────────────────┬──────────────────────────────┘
                       │ セッション → エージェントループ
                       ▼
┌──────────────────────────────────────────────────────┐
│              Agent Runtime (Pi Framework)             │
│                                                      │
│   コンテキスト組立 → LLM推論 → ツール実行 → 応答      │
│        ↑                           │                 │
│   ┌────┴────┐              ┌───────┴──────┐         │
│   │ Memory  │              │   Skills     │         │
│   │ (*.md)  │              │  (SKILL.md)  │         │
│   └─────────┘              └──────────────┘         │
└──────────────────────────────────────────────────────┘
```

---

## 1. Gateway — メッセージの入口と制御面

Gatewayは全メッセージの入口/出口であり、デーモンとして常駐する。

**内部コンポーネント:**

- **Session Registry** — チャネル×ユーザーの組み合わせでセッションを管理
- **Command Queue** — セッションごとにメッセージを直列化（後述）
- **Event Broadcaster** — 各コンポーネントへのイベント配信
- **Heartbeat Runner** — 定期的なプロアクティブチェック（後述）
- **Cron Scheduler** — 時間ベースの自動タスク（後述）

**ポイント:** Gatewayはインターフェース層とエージェント層を分離している。どのチャネルから来ても同じエージェントに届く。

## 2. Agent Runtime — エージェントループ

OpenClawは独自のエージェントランタイムを持たず、**Pi エージェントフレームワーク**（Mario Zechner 作）の上に構築されている。

### Pi フレームワークの構成

| パッケージ（`@mariozechner/` スコープ） | 役割 |
|-----------|------|
| `pi-ai` | LLM通信（API呼び出し） |
| `pi-agent-core` | エージェントループ + ツール呼び出し |
| `pi-coding-agent` | コーディングエージェント + 組み込みツール + セッション永続化 |
| `pi-tui` | ターミナルUI |

OpenClawは `pi-coding-agent` の上にGateway・オーケストレーション・統合層を構築している。

### エージェントループの流れ（ReActパターン）

```
メッセージ到着
  ↓
1. コンテキスト組立（セッション履歴 + メモリ + スキル一覧）
  ↓
2. LLM推論（選択したプロバイダーにAPI呼び出し）
  ↓
3. ツール実行（LLMが選んだツールを実行）
  ↓
4. 結果観察 → 追加アクションが必要なら 2 に戻る
  ↓
5. 応答をチャネルに返却
  ↓
6. 会話履歴 + メモリを永続化
```

これは **ReAct（Reasoning + Acting）パターン** — 推論→行動→観察を繰り返す。

### Command Queue（直列化）

- **レーン方式の FIFO キュー**: `src/process/command-queue.ts` に実装
- セッション単位で直列化（同一セッションでは1つのエージェント実行しか同時に走らない）
- 異なるセッション間では並行実行を許可
- グローバルレーン（`main`）で全体の並行度もキャップ（デフォルト: main=4, subagent=8）
- 純粋な TypeScript + Promises。外部依存やワーカースレッドなし

> **セキュリティ上の意味:** セッション直列化により、同一セッション内でのツール競合や状態不整合を防止。

## 3. Skills — 拡張システム

スキルはOpenClawの核心的な拡張機構。本質は**Markdown指示ファイル**であり、エージェントへの手順書として機能する。MCPサーバーをラップするスキルも多いが（具体的な割合は未確認）、MCPなしの純粋なプロンプトスキルも存在する。

### SKILL.md の構造

```yaml
---
name: todoist-cli
description: "Manage Todoist tasks from the command line."
version: 1.2.0
metadata:
  openclaw:
    requires:
      env:
        - TODOIST_API_KEY     # 必要な環境変数
      bins:
        - curl                # 必要なCLIバイナリ
    primaryEnv: TODOIST_API_KEY
    emoji: "✅"
    homepage: https://github.com/example/todoist-cli
---

# Todoist CLI スキル

（ここにLLMへの指示を自然言語で書く）
```

### スキルの読み込みと優先順位

1. `<workspace>/skills` — 最優先（ワークスペースローカル）
2. `~/.openclaw/skills` — ユーザーレベル
3. バンドルスキル — 最低優先

ファイルウォッチャーが **250ms以内** に変更を検知するため、編集→テストのサイクルが速い。

### スキルとMCPの関係

- ClawHub上のアクティブなスキルの多くが内部でMCPサーバーをラップ（「65%以上」という数字は確認できず）
- MCP型スキルの場合: スキルを有効化 → OpenClawがそのMCPサーバーに接続 → ツールがエージェントに公開
- 例: `serpapi-mcp` をインストール → MCPサーバーが検索リクエストを処理 + SKILL.mdがエージェントに使い方を教える
- 非MCP型スキル: SKILL.mdの指示だけで構成。既存のビルトインツール（exec, read, write等）を組み合わせてタスクを実行する

### スキルのプロンプト注入

スキルが有効な場合、OpenClawはコンパクトなXMLリストとしてシステムプロンプトに注入する。

### ClawHub（スキルレジストリ）

- 13,700+ のサードパーティスキル（2026年3月時点）
- VirusTotalによる自動スキャン
- メタデータの整合性チェック（宣言と実際の動作の一致を検証）
- ライセンス: 全スキルが **MIT-0**（帰属表示不要）
- バンドルサイズ上限: 50MB

### セキュリティ上の制約

- フロントマターで宣言された環境変数・バイナリのみが実行時にアクセス可能（建前上）
- ClawHubのセキュリティ分析が宣言と実際のコードの不一致を検出
- ただし **ClawHavoc攻撃（2026/2）で340+の悪意あるスキルが通過した** 実績あり → 自動スキャンだけでは不十分

## 4. Memory — ファイルベースの記憶

メモリは**プレーンMarkdownファイル**として `~/.openclaw/workspace` に保存される。

### ファイル構造

| ファイル | 役割 |
|---------|------|
| `MEMORY.md` | 長期記憶（決定事項、好み、永続的な事実） |
| `memory/YYYY-MM-DD.md` | 日次ログ（追記のみ） |

- セッション開始時に「今日 + 昨日」の日次ログを読み込む
- `MEMORY.md` と `memory.md` が両方ある場合、大文字版のみ読み込む

### メモリツール

エージェントが使える2つのツール:

- **memory_search** — セマンティック検索（ベクトルインデックス + BM25のハイブリッド検索）
- **memory_get** — 特定ファイル/行範囲の直接読み取り

### コンテキストコンパクション

セッションが長くなりトークン上限に近づくと、OpenClawは自動コンパクションを実行。その直前に「重要な情報をメモリに書き出す」サイレントターンを挟む。

### 埋め込みプロバイダー

OpenAI, Gemini, Voyage, Mistral, Ollama, ローカルGGUFモデルなど複数対応。

> **セキュリティ上の意味:** メモリファイルはプレーンテキストで `~/.openclaw/workspace` に保存される。ファイルシステムアクセスがあれば読み書き可能 → メモリ汚染のリスク。

## 5. Heartbeat & Cron — プロアクティブ動作

### Heartbeat（意識のチェックイン）

- **30分ごと**にエージェントが自発的にターンを実行（デフォルト。Anthropic OAuth認証時は1時間）
- `HEARTBEAT.md` を読んで「何か対応すべきことがあるか？」を判断
- 何もなければ `HEARTBEAT_OK` を返し、ユーザーにはメッセージを送らない
- メインセッションのフルコンテキストにアクセス可能 → 賢い判断ができる

**ユースケース:** メール受信チェック、カレンダー確認、プロジェクト状態の監視など

### Cron（時計仕掛けの実行）

- Unix標準の5フィールドcron式（分 時 日 月 曜日）
- **分離セッション**で実行可能（メインコンテキストに影響しない）
- Heartbeatと違い、条件に関係なく指定時刻に必ず実行

### 使い分け

| | Heartbeat | Cron |
|---|-----------|------|
| トリガー | 定期（30分ごと） | 正確な時刻 |
| 判断 | あり（何もなければ黙る） | なし（必ず実行） |
| セッション | メインセッション | 分離可能 |
| 用途 | 監視・気づき | 定時タスク |

## アーキテクチャ上のセキュリティ示唆

この構造から見えてくるセキュリティ上のポイント:

1. **広い権限の根源** — エージェントループがファイルシステム、ターミナル、ネットワークにアクセスできるのは「ツール」として公開されているから。スキルを絞ればツールも絞れる
2. **スキルはサプライチェーン** — ClawHub経由のスキルは事実上サードパーティコードの実行。ClawHavoc攻撃が示したように自動スキャンには限界がある
3. **メモリは平文** — `~/.openclaw/workspace` にMarkdownで保存。暗号化なし
4. **Heartbeatは自律行動** — ユーザーの明示的な指示なしにエージェントが動く。HEARTBEAT.mdの内容が汚染されると意図しない動作が起こりうる
5. **Pi依存** — コアのエージェントループはPiフレームワーク。PiのセキュリティがそのままOpenClawのセキュリティになる
6. **セッション直列化は防御** — 同一セッション内の競合条件を排除。ただしセッション間の分離がどの程度かは要確認
