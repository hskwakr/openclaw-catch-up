# セキュリティ対照比較: OpenClawの既知リスクはZeroClawでどうなるか

*2026-03-24 作成*

## このノートの位置づけ

ノート03・04でOpenClawのセキュリティを部分的に触れたが、「何が起きて、なぜ起きて、今どうなっていて、ZeroClawでは同じことが起きるのか」を体系的にまとめていなかった。ここではOpenClawの既知リスクを1つずつ取り上げ、ZeroClawで同じリスクがあるかを対照する。

---

## 1. CVE-2026-25253 — ワンクリックRCE（CVSS 8.8）

### OpenClawで何が起きたか

OpenClawのローカルサーバーがWebSocket接続のオリジンヘッダーを検証していなかった。加えてデフォルトで `0.0.0.0:18789`（全インターフェース）にバインドしていたため、グローバルに公開される状態だった。

**攻撃チェーン**: 悪意あるWebページを開く → クロスサイトWebSocketハイジャック → トークン窃取 → ユーザー確認を無効化 → ミリ秒単位でRCE

**影響規模**: 40,000+のインスタンスが露出、うち約63%（25,000+）がリモートから攻撃可能と評価。

**根本原因**: WebSocketオリジン検証の欠如が主因。加えてデフォルトで `0.0.0.0:18789`（全インターフェース）にバインドしていたためリモート攻撃が容易だったが、**localhostバインドでもクロスサイトWebSocketハイジャック自体は成立する**（ブラウザはWebSocketの同一オリジンポリシーを強制しないため）。OpenClawの「No Plan Mode」（速度優先）開発方針に起因するとされる。

**現在のステータス**: 修正済み（パッチ適用後のバージョンではlocalhostバインドがデフォルト）。

### ZeroClawでは？

- ZeroClawはデフォルトで `127.0.0.1`（localhost専用）にバインド — リモートからの直接攻撃は不成立
- 公開IPへのバインドには明示的な設定変更が必要
- アーキテクチャが異なる（Rust製ゲートウェイ、異なるWebSocket実装）
- ⚠️ ただしlocalhostバインドでもクロスサイトWebSocketハイジャックは理論上可能（オリジン検証の実装に依存）

**判定: リモート攻撃のリスクは大幅に低減。** ただしローカル環境からのクロスサイト攻撃への耐性はオリジン検証の実装次第。

## 2. CVE-2026-26327 — 認証バイパス

### OpenClawで何が起きたか

iOS/macOSクライアントがmDNS/DNS-SDサービスディスカバリーのTXTレコードを未検証のまま信頼していた（CWE-345）。攻撃者が同一ネットワーク上からTXTレコードを偽装し、TLS証明書ピンニングをバイパス、認証情報を漏洩させることが可能だった。

**根本原因**: サービスディスカバリーで取得したデータの検証不足。

**現在のステータス**: 修正済み。

### ZeroClawでは？

- ZeroClawのmDNS/DNS-SD実装の詳細は公開情報が限定的
- 同等の脆弱性は報告されていないが、サービスディスカバリーを使う場合は理論的に同種のリスクがありうる

**判定: 検証不能。** ZeroClawのサービスディスカバリー実装が公開されていないため、同じ問題があるかどうか判断できない。

## 3. ClawHavoc事件（2026年2月）— サプライチェーン攻撃

### OpenClawで何が起きたか

ClawHub（OpenClawのスキルマーケットプレイス）に悪意あるスキルが登録された。初期発見時は341スキル、その後マーケットプレイス拡大に伴い824+に増加。VirusTotalの自動スキャンを通過（攻撃はSKILL.md内のソーシャルエンジニアリングと外部ペイロード配信に依存し、スキルファイル自体にマルウェアを埋め込まない手法のため）。ペイロードはAtomic macOS Stealer（AMOS）+ Windowsキーロガー/RAT。Solanaウォレット関連（111スキル）、YouTubeユーティリティ（57スキル）、auto-updater（28スキル）など。

**根本原因**: 自動スキャンだけに依存するマーケットプレイスのセキュリティモデル。サードパーティコードの実行を前提とするエコシステム設計。

**現在のステータス**: ClawHubのスキャン強化、メタデータ整合性チェック追加。ただし新たな悪意あるスキルの登録は構造的に防ぎきれない。全スキルの41.7%に脆弱性があるという調査結果も（**ClawSecure**による監査。2,890+スキルを対象）。

### ZeroClawでは？

- **ZeroClawにはプラグインマーケットプレイスが存在しない** — 設計上の判断として意図的に排除
- スキルはワークスペース内で手動管理
- `zeroclaw skills audit` コマンドでシンボリックリンク、危険なMarkdownパターン、シェルペイロードを静的解析

**判定: 構造的に排除済み。** マーケットプレイスがないため、ClawHavoc型の攻撃は不可能。

## 4. ホストレベルアクセス — SSH鍵・クラウド認証情報への到達

### OpenClawで何が起きたか

OpenClawはホストユーザーの権限で動作し、`~/.ssh`、`~/.aws/credentials`、クラウドサービストークンなど全てにアクセス可能。明示的にサンドボックスを設定しない限り制限されない。

**根本原因**: allow-by-default のアクセスモデル。セキュリティはユーザーが自ら設定する必要がある。

**現在のステータス**: `tools.deny`、`tools.profile: "minimal"` 等で制限可能だが、デフォルトでは制限なし。

### ZeroClawでは？

- **ワークスペース分離**: `workspace_only = true` がデフォルトで、ファイル操作はワークスペース内に制限
- **禁止パスのハードコード**: `/etc`, `/root`, `/proc`, `/sys`, `~/.ssh`, `~/.gnupg`, `~/.aws` — 14のシステムディレクトリ + 4の機密ドットファイルがデフォルトでブロック。設定で上書き不可
- **パストラバーサル防止**: `..` シーケンスと絶対パスを拒否、シンボリックリンク脱出はパス正規化で検出

**~~⚠️ 重要な発見: Issue #3983 — サンドボックスが機能していない~~　→ 解決済み（PR #3989、2026-03-19マージ）**

ZeroClawの設定には `[security.sandbox]` セクション（Firejail、Bubblewrap、Landlock、Docker等のバックエンド対応）がある。~~以前はシェルコマンド実行時にサンドボックスが実際には適用されておらず、単体テストは存在するが統合レベルでは死んだコードになっていた。~~

PR #3989で以下が修正された:
- ShellToolに `Arc<dyn Sandbox>` フィールドを追加（依存注入）
- シェルコマンド実行時に `sandbox.wrap_command()` を呼び出すように変更
- `all_tools_with_runtime()` でセキュリティ設定からサンドボックスを生成しShellToolに渡す
- 統合テスト追加（43テスト全パス）

**判定: ファイル操作ツール・シェル実行の両方でアクセス制限が機能している（OpenClawより大幅に良い）。**

## 5. メモリの平文保存

### OpenClawで何が起きたか

`~/.openclaw/workspace/MEMORY.md` に長期記憶がプレーンテキストで保存される。暗号化なし。情報窃取マルウェアが `.openclaw/` ディレクトリを標的にしているという報告あり。プロンプトインジェクションでMEMORY.mdに悪意あるペイロードを書き込むことも理論上可能。

**根本原因**: 平文ファイルベースの記憶設計。

**現在のステータス**: 変更なし。暗号化は導入されていない。

### ZeroClawでは？

- **ChaCha20-Poly1305 AEAD暗号化**: シークレットをディスク上で暗号化
- 秘密鍵は `<workspace>/.zeroclaw/secret_store.key`（パーミッション 0o600）
- ただし実行時にはメモリ上に平文で展開される（機能上不可避）

**判定: ディスク上の保存はOpenClawより安全。ランタイムメモリ上の平文は両者共通の制約。**

## 6. Heartbeat — ユーザー指示なしの自律実行

### OpenClawで何が起きたか

30分ごと（デフォルト）にエージェントが自発的にターンを実行。HEARTBEAT.mdを読んで判断し、アクションを起こす。HEARTBEAT.mdが汚染されると意図しない動作が起こりうる。

**根本原因**: プロアクティブ動作のための設計。ユーザーの承認なしに行動する能力。

**現在のステータス**: デフォルト有効。無効化は可能。

### ZeroClawでは？

- Heartbeat + Cronスケジューラーは存在する（デーモンモード）
- ただし **AutonomyLevel** による制御が可能:
  - `ReadOnly` — 読み取りのみ、実行なし
  - `Supervised` — 許可リスト内のみ実行
  - `Full` — サンドボックス内でフルアクセス（PR #3989でサンドボックス統合済み）

**判定: 同じ機能があるが、自律レベルの制御はZeroClawの方が細かい。**

## 7. 攻撃面の大きさ

### OpenClaw

- ~430,000-500,000行（TypeScript）
- 25個のビルトインツール + 53個のバンドルスキル
- Node.js依存（C++バインディング経由のメモリ破壊リスク）
- 外部依存が多い

### ZeroClaw

- ~3,000-8,000行（Rust）
- ~120個のツール（⚠️ ツール数自体はOpenClawより多い）
- Rustのメモリ安全性（コンパイル時にバッファオーバーフロー等を排除）
- 3.4MBバイナリ、ピークRSS 8MB未満
- Clippy静的解析 + ファジング + 1,017テスト（コードカバレッジ85%+）

**ただしRustが防げないもの:**
- ロジックバグ（認証の実装ミス、権限チェック漏れ等）
- インジェクション攻撃（コマンドインジェクション、SQLインジェクション等）
- リソース枯渇（DoS攻撃）
- `unsafe` ブロック内のメモリ安全性違反
- FFI（C言語連携）経由の脆弱性

**判定: コード量は38-54倍小さく、メモリ安全性は確保されている。ただしロジックバグやインジェクションはRustでも起きうる。ツール数（120個）はOpenClaw（25個）より多い点は注意。**

## 8. セキュリティ監査と外部評価

### OpenClaw

- Palo Alto Networksが「セキュリティ上の悪夢」と評価
- Trend Microの詳細分析あり
- CVE 2件が公式に割り当て済み
- ClawHavoc事件でメディア注目

### ZeroClaw

- 公開CVE: **0件**（NVD、GitHub Advisory Database確認）
- 正式な第三者セキュリティ監査: **未実施**（公開情報なし）
- セキュリティベンチマーク: 145攻撃テストで84.1/100スコア（116拒否、22失敗）
- プライベート脆弱性報告（responsible disclosure）ポリシーあり

**判定: ZeroClawのCVE 0件は「安全」ではなく「まだ十分に調べられていない」可能性がある。正式な第三者監査がないことは留意すべき。一方、セキュリティベンチマークでは一定のスコアを達成。**

## 判断に向けて: 何が言えて、何が言えないか

### 言えること

- ZeroClawはOpenClawの**既知の問題のうち大部分を構造的に回避している**（マーケットプレイス排除、deny-by-default、localhost限定、暗号化）
- コードベースが小さく、Rustのメモリ安全性があるため、**同じクラスの脆弱性が発見される確率は低い**
- ただしセキュリティ上の弱点がゼロとは言えない（第三者監査未実施、CVE 0件の意味は不明）

### 言えないこと

- **ZeroClawが「安全」かどうか** — 第三者監査がなく、ユーザー数が少ないため未発見の脆弱性がある可能性
- **CVE 0件の意味** — 「脆弱性がない」のか「探す人がいない」のかは区別できない
- **Rustだから安全** — メモリ安全性はあるが、ロジックバグやインジェクションは防げない
