# ローカルLLMとコスト検討（個人開発補助の前提）

*2026-03-23 作成*

## このノートの位置づけ

前回のフォーク比較で「月間コスト予算」「Claude専用でいいか」が未回答の論点として残っていた。ここではローカルLLMを使う選択肢を中心に、コスト・品質・実用性を整理する。

---

## 1. ローカルLLMの現状（2026年3月時点）

### コーディング用途で有力なモデル

| モデル | パラメータ | 特徴 | HumanEval | VRAM目安（Q4量子化） |
|--------|-----------|------|-----------|---------------------|
| **Qwen 2.5 Coder 32B** | 32B | コーディング特化。GPT-4oレベルと評価される | ~88.4% | ~22-24GB |
| **Qwen3-Coder-Next** | 80B (MoE, 3B active) | MoEで軽量動作。2026年の本命 | — | 要確認 |
| **Qwen 2.5 Coder 14B** | 14B | バランス型。16GB VRAMで動作可 | ~64%（base） | ~10-12GB |
| **Qwen 2.5 Coder 7B** | 7B | 軽量。8GB VRAMで動作可 | — | ~5-6GB |
| **DeepSeek-Coder** | 各種 | 300+言語対応。推論重視 | — | モデルサイズ依存 |
| **DeepSeek R1** | 各種 | Chain-of-thought推論。遅いが深い | — | モデルサイズ依存 |
| **Llama 3.1 8B** | 8B | Meta製。汎用性高い | ~68% | ~5-6GB |

### 実用上のポイント

- **コーディングならQwen 2.5 Coder系が現状最強**。14B以上ならかなり実用的
- ローカルLLMは日常的なコーディングタスク（補完、リファクタ、ドキュメント生成、テスト作成、デバッグ）の大部分をカバーできるレベルに到達（「70-80%」という数字はコミュニティの経験則であり、学術的裏付けはない）
- 残り20-30%（複雑なアーキテクチャ設計、大規模コードベースの理解、長文脈推論）はまだクラウドLLMが優位

## 2. ハードウェア要件

### GPU VRAM別の選択肢

| VRAM | 動かせるモデル | 実用度 |
|------|--------------|--------|
| **8GB**（RTX 3060/4060等） | 7Bモデル（Q4量子化） | 軽いタスクならOK。複雑な推論は厳しい |
| **16GB**（RTX 4080/4090 16GB等） | 14Bモデル（Q4量子化） | 個人開発補助として十分実用的 |
| **24GB**（RTX 3090/4090） | 32Bモデル（Q4量子化） | GPT-4oレベル。ほぼ全用途をカバー |
| **GPU なし（CPU推論）** | 7B程度 | 遅い（数秒/トークン）が動く |

### Ollama の仕組み

- モデルをVRAMに載りきらない場合、自動でGPU/CPU間でレイヤーを分割（部分オフロード）
- Q4_K_M量子化がデフォルト。FP16比で約75%のVRAM削減、品質の劣化は軽微
- コンテキスト長: OpenClawは最低64Kトークンを要求する → モデルとコンテキストの両方がVRAMを消費するので注意

## 3. 各フォークのローカルLLM対応

### OpenClaw

- **Ollamaネイティブ対応**（2026年3月に公式プロバイダーとなった）
- 設定で `baseUrl` パラメータを指定して接続
- ストリーミングレスポンスとツールコールを同時サポート
- 注意: ベースのシステムプロンプト(3,000-5,000トークン) + ツール定義(23ツール分)で合計最大~15,000トークンが毎回送信される → ローカルLLMでもこのオーバーヘッドは同じ。推論速度に影響

### ZeroClaw

- **Ollamaネイティブ対応**（22+プロバイダー対応のひとつ）
- 単一バイナリ + Ollama で完結。追加依存なし
- ZeroClaw自体は4MBしかRAMを使わない → ほぼすべてのリソースをLLMに回せる
- ツール定義が少ないためシステムプロンプトのオーバーヘッドが小さい
- **llama3.1:8bなら合計6GB程度のRAMで動作する実績あり**

### NanoClaw

- **Ollamaを「MCPツール」として利用**する方式（ネイティブプロバイダーではない）
- `/add-ollama-tool` スキルでコンテナ内からローカルOllamaに接続
- `ollama_list_models` と `ollama_generate` の2ツールが追加される
- **Claude がオーケストレーター、Ollamaが下請け**という構成
  - Claudeが毎回のやりとりを処理し、必要に応じてOllamaに委任する
- ⚠️ **すべてのやりとりがClaude APIを経由する**ため、コスト削減効果は限定的。Claude APIコストはほぼそのまま発生する

## 4. コスト比較: Claude API vs ローカルLLM

### 前提: 個人の開発補助、日に数十回のやりとり

#### Claude API（直接利用の場合）

| プラン | 月額 | 備考 |
|--------|------|------|
| Pro（サブスク） | $20/月 | チャットUI経由。レート制限あり |
| Max 5x | $100/月 | API相当$100超の利用者に有利 |
| API従量課金（Sonnet） | $3/1M入力, $15/1M出力 | Claude Code利用者は平均$6/日 ≒ $130-180/月 |
| API従量課金（Haiku） | $1/1M入力, $5/1M出力 | 軽量タスクならかなり安い |

#### ローカルLLM（Ollama）

| 項目 | コスト |
|------|-------|
| GPU（既に持っている場合） | $0/月 |
| 電気代（RTX 4090で1日6時間稼働） | ~$5-15/月（地域による） |
| VPS上で動かす場合（GPU付き） | $30-100+/月 |
| **合計（自宅GPU）** | **電気代のみ** |

#### ハイブリッド構成（NanoClaw方式）

| 項目 | コスト |
|------|-------|
| Claude API（オーケストレーター） | **ほぼ通常通り発生**（すべてのやりとりがClaude経由のため） |
| ローカルLLM（下請け） | 電気代のみ |
| **合計** | **Claude API利用料 + 電気代**（大幅な削減は見込めない） |

### コスト判断のまとめ

- **GPUを持っている → ローカルLLM一択がコスト最安**。ZeroClawかOpenClaw + Ollamaで月額ほぼ$0
- **GPUがない → Claude Pro ($20/月) が現実的**。ローカルはCPU推論で遅すぎて実用的でない
- **品質を落としたくない → Claude Pro/Max**。NanoClawハイブリッド方式は仕組み上Claude APIコストを大幅には削減できないため、コスト面でのメリットは薄い

## 5. 品質面のトレードオフ

### ローカルLLMが得意なこと

- コード補完・リファクタリング
- テスト生成
- ドキュメント・コメント生成
- 定型的なバグ修正
- 翻訳・要約

### まだクラウドLLM（Claude/GPT-4o）が優位なこと

- 大規模コードベースの横断的な理解（コンテキスト長の壁）
- 複雑なアーキテクチャ設計の議論
- 曖昧な要件からの仕様策定
- マルチステップの推論チェーン
- ツールコールの信頼性（ローカルLLMはツールコールの精度がまだ不安定な場合がある）

## 6. 構成オプション整理

### Option A: ZeroClaw + Ollama（完全ローカル）

- コスト: 電気代のみ
- 必要: GPU（16GB+ VRAM推奨）
- メリット: プライバシー完全、コストゼロ、高速
- デメリット: 品質はモデルサイズに依存。32B未満だと複雑なタスクで限界

### Option B: OpenClaw + Ollama（完全ローカル）

- コスト: 電気代のみ
- 必要: GPU + それなりのRAM（Node.jsオーバーヘッド）
- メリット: プラグインエコシステム利用可能
- デメリット: セキュリティリスク、トークンオーバーヘッドが大きい

### Option C: NanoClaw + Claude + Ollama（ハイブリッド）

- コスト: Claude APIコスト（⚠️ すべてのやりとりがClaude経由のため大幅削減は見込めない）
- 必要: GPU + Claude API キー
- メリット: コンテナ分離によるセキュリティ + 一部の定型処理をローカルに委任可能
- デメリット: コスト削減効果が限定的、Claude専用、構成が複雑

### Option D: Claude Pro/Max のみ（クラウドのみ）

- コスト: $20-200/月
- 必要: なし（ブラウザだけ）
- メリット: セットアップ不要、最高品質
- デメリット: コスト固定、プライバシー、レート制限

## 7. Akiraの環境: M4 Mac Mini 16GB での現実的な選択肢

### Apple Siliconの特徴

- **ユニファイドメモリ**: CPU/GPUがメモリを共有。16GBの全量をLLM推論に使える（NVIDIAのVRAMとは違う）
- **Metal Performance Shaders**: Ollamaが対応済み。GPU推論が効く
- **制約**: 16GBのうちOSとアプリで3-4GB使うので、LLMに使えるのは実質12-13GB程度

### 16GBで動かせるモデル

| モデル | 量子化 | メモリ使用量 | 実用度 |
|--------|--------|-------------|--------|
| **Qwen 2.5 Coder 7B** | Q4_K_M | ~5-6GB | ◎ 快適。軽いコーディングタスクに十分 |
| **Qwen 2.5 Coder 14B** | Q4_K_M | ~10-12GB | △ 動くがギリギリ。コンテキスト長を短くする必要あり |
| **Qwen 2.5 Coder 32B** | Q4_K_M | ~22-24GB | ✕ メモリ不足で動かない |
| **DeepSeek-Coder 6.7B** | Q4_K_M | ~5GB | ◎ 快適 |
| **Llama 3.1 8B** | Q4_K_M | ~5-6GB | ◎ 快適。汎用性高い |

### 現実的な評価

- **7Bモデルがスイートスポット**。快適に動き、コード補完・リファクタ・テスト生成は十分
- **14Bは挑戦的**。動くが、コンテキスト長を短く制限する必要があり、OpenClawのシステムプロンプト（5,000-10,000トークン）を加えると実用的なコンテキストが狭くなる
- **32Bは無理**。32GB以上のMac Miniでないと現実的でない

### 16GBでの推奨構成

**Option A' (推奨): ZeroClaw + Ollama + Qwen 2.5 Coder 7B**
- ZeroClawはシステムプロンプトが軽い → 7Bモデルでもコンテキストを有効に使える
- コスト: 電気代のみ（Mac Miniは低消費電力なので月$2-3程度）
- 日常的なコーディングタスクの大部分をカバー
- 複雑なタスクはClaude Pro ($20/月) を併用するのが現実的

**Option C' (代替): NanoClaw + Claude + Ollama 7B（ハイブリッド）**
- コンテナ分離というセキュリティ上のメリット
- ⚠️ すべてのやりとりがClaude APIを経由するため、コスト削減効果は限定的
- メリットはセキュリティであり、コスト削減ではない

**Option D は引き続き有効**: Claude Pro/Max のみ（$20-200/月、セットアップ不要）
